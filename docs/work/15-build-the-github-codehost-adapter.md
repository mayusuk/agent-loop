## Summary

Adds the GitHub `CodeHost` in `internal/adapters/github` for pull requests: change lookup and branch naming, opening changes, labels, the change feed, reviews with finding threads and the status table, finding resolves and replies, manual comments with their clearing rules, gates, `ContainsBase` and the pinned merge. It reuses the shared client from T9, and the stub GitHub (`githubtest`) grows a small git model, pull requests, reviews, threads, statuses and branch rules so the conformance suite runs against it. `Trust` and pusher attribution are T11.

## Approach

**`internal/adapters/github`**
- `labels.go`: the marker-to-label maps, shared by the tracker and the host.
- `host.go`: `Host` and `HostConfig` (labels, identities, base branch, branch prefix, profile gates, manual-comment bots, feed page size). `Capabilities`, `Validate`, `Change`, `ChangeForItem` (record and branch name, `-<n>` branches, then closing references), `OpenChange` (looked up by key among pull requests on the branch), `SetLabel`, `ContainsBase` (compare), `Merge` (pinned SHA, outcome mapping) and a placeholder `Trust` (D13).
- `gates.go`: required gates from the branch rules and classic protection, or the profile list; results from check runs and commit statuses on the commit asked for.
- `reviews.go`: `ReviewRecords`, `PostReview` (placement by the diff, finding IDs in finding records, the status table), `ResolveFinding`, `PostReply`, `ManualComments` with the clearing rules.
- `hostfeed.go`: `Changes` from the open pull requests and the `issues?since` catch-all, with batched GraphQL detail (timeline, threads, head gates).

**`internal/adapters/github/githubtest`**: a small git model (commits with file snapshots, branches, compare, contents and merges), pull requests, review comments and threads, reviews and dismissals, commit statuses and check runs, branch rules and classic protection, the merge endpoint with GitHub's refusals, and the GraphQL queries and mutations the host sends. The `Driver` gets its code-host actions (the trust ones stay `ErrNotYet` until T11).

**`conformance/`**: `RunWithoutTrust` runs every case except C10, C13 and C15. C6 dismisses `CHANGES_REQUESTED` reviews (D11).

## Acceptance criteria

- Fixture-based unit tests cover every method, including the merge response mapping (200 → `Merged`, 409 → `HeadMoved`, 405 → `NotMergeable`, anything else → `Failed`).

- Manual-comment clearing tests cover a human resolve, an identity's resolve, an unresolve, a dismissal and an empty `CHANGES_REQUESTED` review (C6, TestFR7AC9_...).

## Decisions

- **D1** [gap] INTEGRATION-SPEC §6.2, §3.3, §8.3: `OpenChange` writes the change record with `item` set to `NewChange.Item` and `n` taken from the branch (1 for `<prefix><item>`, *k* for `<prefix><item>-<k>`) when the record leaves them out; a record naming another item is `ErrConflict`. It posts as the given identity, which must be the coder (the record type's author), else `ErrPermission`. The title is `NewChange.Title`, or `agent-loop: #<item>` when empty (GitHub refuses an empty title). Before writing it looks for a pull request, open or closed, whose head is the branch and whose body has a coder `change` record with the key. A missing branch is `ErrNotFound`; the base branch, or another open pull request on the branch, is `ErrConflict` (fake D8).
- **D2** [gap] INTEGRATION-SPEC §6.2: `ChangeForItem` tries `<prefix><item>`, then `-2`, `-3` and so on, stopping at the first name with no pull request (as tracker D7), and returns the lowest-numbered open pull request whose body has a coder `change` record naming the item on the branch its `n` gives (either name when `n` is missing). If there is none, it returns the lowest-numbered open pull request in the issue's `closedByPullRequestsReferences`. `Change.Item` is the record's item when the branch matches, else the first closing reference, else empty.
- **D3** [gap] INTEGRATION-SPEC §6.3, I8, I16, §5.2: the adapter sets `id` in each finding record (another `id` is `ErrConflict`). The diff is `GET /pulls/{n}/files`: a line counts as in the diff when it is on the new side of a hunk in the file's `patch`. A finding with a path and a line in the diff is an inline comment on that line; with a path in the diff and no line, a line outside the diff, or a file with no patch, a file-level comment (`subject_type: file`) whose text starts with `` `path:line` `` when there is a line; with a path not in the diff, or no path, a section of the review text that starts with the location. A comment's text is `**F3** (score 4, open)`, the body, then the finding record. Review-text findings have no record of their own: the review record's `findings` is theirs.
- **D4** [gap] INTEGRATION-SPEC §6.3: the review body is the summary, the review-text findings, the status table, then the review record. The table has one row per entry of the record's `findings` (id, score, status), in that order, then each posted finding the record leaves out. *Where* is `path:line`, `path (file)` or `no file`; for findings posted earlier with a thread, it links the thread's first comment. New findings aren't linked, since their comments don't exist until the review is posted. With no findings there is no table.
- **D5** [gap] INTEGRATION-SPEC §8.3: `ReviewRef` is the REST review ID and `ThreadRef` the review thread's GraphQL node ID (the resolve mutations take it). A review record counts when the reviewer identity submitted the review and its body ends with a `review` record. `ReviewRecord.Threads` maps each finding posted with that review (a thread whose first comment is the reviewer's, in that review, with a finding record) to its thread. `PostReview` looks the key up among the change's reviews by the reviewer, posts `APPROVE` or `COMMENT` on `ReviewPost.Commit`, and builds the body from the record (D4).
- **D6** [gap] INTEGRATION-SPEC §6.3, §8.3: `ResolveFinding` resolves the finding's thread (D5) as the reviewer with `resolveReviewThread`, unless it is already resolved, so a human's resolve is never replaced. A finding known only from a review record's `findings` (no thread) does nothing; an unknown finding is `ErrNotFound` (fake D8).
- **D7** [gap] INTEGRATION-SPEC §6.4, fake D3: `PostReply` to a thread replies to the thread's first comment (`POST /pulls/{n}/comments/{id}/replies`) as the coder; to `ThreadRef(<change>)` it posts a conversation comment. It looks the key up among the coder's comments in that place first. The text is the body, then the record. A thread on another change is `ErrNotFound`.
- **D8** [gap] INTEGRATION-SPEC §9.6, §8.3: a manual comment's ID is `MC-<comment id>` for a review comment and `MC-R<review id>` for a review body (GitHub's comment and review IDs are separate sequences). A manual commenter is an account of type `User` that isn't one of the identities, or a bot whose login, with or without `[bot]`, is in `manual_comment_bots`. A body of only whitespace is empty. A dismissed review's kind uses its state before the dismissal (`ReviewDismissedEvent.previousReviewState`), since a dismissed review's REST state is `DISMISSED`. GraphQL bot logins get `[bot]` appended, so actors match the REST ones.
- **D9** [gap] INTEGRATION-SPEC §9.6 ("a comment added to a thread after a human resolved it blocks"), C6: GitHub doesn't say when a thread was resolved (`PullRequestReviewThread` has `resolvedBy` but no time, and no timeline event), so the adapter can't tell a comment made before a resolve from one made after it. It keeps, per thread, what it observed on each `ManualComments` and `Changes` call (resolved or not, by whom, the newest comment ID), and the change-feed cursor carries it across restarts. A human's resolve clears only the comments that were already there when the thread was last seen unresolved, or last seen resolved by someone else; a comment first seen with the thread already resolved by a human keeps blocking until the thread is seen unresolved and resolved again. A thread first seen already resolved (after a feed reset) clears nothing. This never clears a comment made after a resolve, at the cost that a comment made and resolved between two observations needs a second resolve. The owner should confirm this reading, or choose another (for example, clearing every comment in a human-resolved thread).
- **D10** [gap] INTEGRATION-SPEC §9.6: a thread is cleared by a human when `isResolved` and `resolvedBy` is a `User` that isn't an identity; a `null` `resolvedBy` or a bot clears nothing. A review body is cleared when the review is `DISMISSED` and its latest `ReviewDismissedEvent.actor` is a `User` that isn't an identity.
- **D11** [open] INTEGRATION-SPEC §9.6, C6: GitHub dismisses only `APPROVED` and `CHANGES_REQUESTED` reviews, so a human's non-empty `COMMENTED` review body can be cleared on GitHub only by an `addressed` ruling. C6 now dismisses two `CHANGES_REQUESTED` reviews, which the fake passes as before. The spec should say this in §9.6.
- **D12** [gap] INTEGRATION-SPEC §9.7, fake D10: the required gates are the profile's `gates` when set, else the `required_status_checks` contexts of `GET /rules/branches/{base}` and of classic protection (`GET /branches/{base}/protection/required_status_checks`, 404 meaning none), in that order without repeats. On the commit asked for, a gate's result is its latest check run (highest ID) from `GET /commits/{c}/check-runs`, else its status from `GET /commits/{c}/status`. A check run that isn't `completed` is `Pending`; one completed with `success`, `neutral` or `skipped` is `Pass`; any other conclusion is `Fail`. A status `success` is `Pass`, `pending` is `Pending`, `failure` and `error` are `Fail`. Neither is `Missing`. A change that doesn't exist is `ErrNotFound`.
- **D13** [gap] Plan T10/T11: until T11, `Trust` reports `ruleset_missing` for every commit on the head that isn't reachable from the base tip (`GET /compare/{base}...{head}`), so nothing is trusted, and `HeadMoved.Pusher` is `unknown`. `Validate` reports `wrong_adapter`, `wrong_repo`, `base_branch_missing` (`GET /branches/{base}` is 404) and `merge_method_unsupported`; permission and ruleset checks are T11.
- **D14** [gap] Plan T10 "fixtures", tracker D14: the stub assumes, and the live run must confirm, that: a reply in a review thread creates a `COMMENTED` review with an empty body; a review with an empty body is accepted for every event (GitHub documents a body as required for `COMMENT` and `REQUEST_CHANGES`, so the live run may refuse C16's empty reviews); resolving or unresolving a thread and a new check result don't change a pull request's `updated_at`; a pushed commit appears as one `PullRequestCommit` timeline item dated by its commit; merging a pull request adds a `MergedEvent` and a `ClosedEvent`; `GET /pulls/{n}/files` patches use unified hunks.
- **D15** [gap] INTEGRATION-SPEC §9.7, I15, fake D8: `Merge` first reads the pull request: merged with its head at `pinned` is `Merged` (a repeat), merged at another commit or closed is `NotMergeable`. Then it calls `PUT /pulls/{n}/merge` as the loop with `sha` and `merge_method` (`squash` when empty). 200 is `Merged`, 409 `HeadMoved`, 405 `NotMergeable`. 5xx responses, network failures and rate limits are returned as `ErrTransient` or `ErrRateLimited`, so the activity retries and the retry finds a merge that went through. Any other response (403, 404, 422 and so on) is `Failed`, with no error.
- **D16** [gap] INTEGRATION-SPEC §9.4, fake D2: the change feed reads the open pull requests (`GET /pulls?state=open`) and the pull requests in `GET /issues?state=all&since=<window start>&sort=updated`, then their detail in batched GraphQL queries (timeline items, review threads, the head's check contexts). Open pull requests are read every poll, unlike the spec's "only pull requests the REST feeds show as changed", because thread resolves and check results don't change a pull request's `updated_at` (D14). Events: each `PullRequestCommit` is a `HeadMoved` to that commit; `MergedEvent`, `ClosedEvent` (except the one a merge makes), `ReopenedEvent`, `PullRequestReview` (`ReviewSubmitted`) and `ReviewDismissedEvent` map one to one; a pull request created in the window is `Opened`; a thread's resolved state differing from the cursor's is `ThreadResolved` (actor `resolvedBy`) or `ThreadUnresolved` (no actor: GitHub doesn't record who unresolved); a change in the head's check contexts is `GateChanged`. The cursor is `gh1h:` and base64url JSON of the window start and, per pull request still open or updated in the window, its timeline items seen, its threads' state (D9) and its gate digest. Each call returns at most one page, oldest first by time, each pull request's events in timeline order; the window start moves to the newest `updated_at` read only when a call returns everything pending. A pull request not in the cursor counts the timeline items dated at or after the window start (commits only after it was created). An unreadable cursor is `ErrConflict`.
- **D17** [gap] INTEGRATION-SPEC §11, plan T10/T11: `conformance.RunWithoutTrust(t, f)` runs every case but C10, C13 and C15, for a code host whose trust comes later. The GitHub adapter moves to `Run` in T11.
- **D18** [gap] INTEGRATION-SPEC §8.3, §9.2: change labels use the tracker's marker-to-label map; `SetLabel` adds or removes the label as the loop (already set, or already absent, does nothing) and `Change.Markers` maps labels back, ignoring unmapped ones.
- **D19** [gap] conformance `Driver` on GitHub: a push makes one commit through the contents API, on `conformance.ChangedFile`, except that pushes to the base branch change `conformance-base.txt`, so merging the base into a loop branch (`POST /merges`) doesn't conflict on live GitHub; gate results are commit statuses; `RequireApprovals` sets classic protection's required approving review count. Fork branches, tags, rulesets, admins and coder runs stay `ErrNotYet` (or no-ops) until T11.
