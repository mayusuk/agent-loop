# Work plan: Implement the workspace and the local runner with the Claude sandbox

**Issue:** [#18](https://github.com/mayusuk/agent-loop/issues/18) (feature)
**Branch:** `issue/18-implement-the-workspace-and-the-local`
**Base:** `origin/main @ 6ec9fe5` (checked before branching)
**Status:** Done

## Summary

Adds `internal/workspace`, which keeps a cached clone of each repository and prepares a fresh working tree per run on the branch INTEGRATION-SPEC §3.3 says, then deletes it. Adds the `local` `Runner` in `internal/runners`: it starts a handler with a built environment, stdin closed and redacted logs, in its own process group stopped at the time limit, serves git credentials over a per-run socket, writes the run's Claude Code sandbox settings (TECHNICAL-SPEC §7.2) and hands them to the handler in `AGENT_LOOP_CLAUDE_SETTINGS`, and refuses a handler the sandbox doesn't wrap unless the stage is `local-unsandboxed`.

## Approach

**`internal/workspace`** (`Git`, implements `ports.Workspace`):
- Root defaults to `<user cache dir>/agent-loop/workspaces`: `repos/<key>.git` (a bare cached clone per repository URL) and `runs/<slug>-<random>` (one per run).
- `Prepare` locks the cached clone (a `flock` on `repos/<key>.lock`, so two workers on one host don't race), clones it if missing, fetches every branch (`+refs/heads/*:refs/heads/*`, `--prune`), then makes the run's tree with `git clone --shared --no-checkout` from the cache, points `origin` at the real URL, and checks out: a detached commit for review; the remote branch head when the branch exists; otherwise a new branch from the base tip with its upstream set to the same name. Returns the real path (symlinks resolved), the branch and the head.
- The fetch authenticates with an optional token callback, passed to git as an `http.extraHeader` in `GIT_CONFIG_*` environment variables, never in arguments. Git runs with no system or global config and never prompts.
- `Release` removes the run's tree; it refuses a path outside `runs/`, and an already deleted tree is not an error. The branch stays.

**`internal/runners`** (`Local`, implements `ports.Runner`):
- `sandbox.go`: `Settings(SandboxPaths) ([]byte, error)` builds the settings JSON; `DeniedReads(dep, home)` lists the §7.2 reads; `Wrapped(command)` tells whether the sandbox wraps a handler.
- `credhelper.go`: the per-run socket server (`get` answers the push token for `https` on the repository's host only, nothing otherwise) and the client `CredentialHelperMain`, which `agent-loop credential-helper <socket> <op>` runs.
- `local.go`: `Run` checks the spec, makes the run directory (`<tmp>/al-XXXX/` with `git.sock`, `claude-settings.json` and the writable `tmp/`), configures the helper in the run's tree, builds the environment from scratch, starts the handler in its own process group with stdin on `/dev/null` and stdout and stderr through the redactor into the log file, stops the group at the time limit (SIGTERM, then SIGKILL after a grace period) and kills what is left of the group when the handler exits.
- `result.go`: `ReadResult(input, outcome)` reads and validates `result.json`; anything missing or invalid is a `failed` result, whatever the exit code.
- `internal/ports`: `RunSpec` gains `RepoURL`, `Runner` and `LogPath`; `PushToken`/`ReadToken` become `Push`/`Read` of a new `TokenSource` interface (which `secrets.Lease` already implements), so the helper serves a renewed token.
- `cmd/agent-loop`: a hidden `credential-helper` subcommand that calls `runners.CredentialHelperMain`.

Tests use the test binary itself as the fake handler and the helper client (dispatched from `TestMain`), a symlink named `agent-loop-claude` for the sandboxed path, local bare repositories as remotes, and no network or `claude`.

## Acceptance criteria

- A handler that never exits is stopped at its time limit, together with every child process (TestNFR7AC1_...).
- A missing or invalid `result.json` gives `failed`, whatever the exit code (TestFR18AC3_...).
- A golden test checks the generated sandbox settings against TECHNICAL-SPEC §7.2.
- The credential helper serves the stage's push token, and nothing for review (INTEGRATION-SPEC §3.4).

## Decisions

- **D1** [gap] TECHNICAL-SPEC §7.2, coordinator note on #18: the `local` runner writes the run's Claude Code settings file and passes its absolute path to the handler in `AGENT_LOOP_CLAUDE_SETTINGS`; the starter handlers run `claude --settings "$AGENT_LOOP_CLAUDE_SETTINGS"` (agent-loop-handlers D12). The variable is not set for `local-unsandboxed`. Why: §7.2 says the runner generates the settings but not how the handler gets them.
- **D2** [ambiguity] TECHNICAL-SPEC §5, §7.2, INTEGRATION-SPEC §3.3: the "fresh worktree per run" is a separate clone made with `git clone --shared` from the cached clone, not a `git worktree`. Why: a `git worktree` keeps its index, refs and new objects in the cached clone, so a handler committing would need write access outside its tree, which §7.2 forbids ("Nothing else"). A shared clone borrows the cache's objects read-only and writes only inside the run's directory. The cached clone has `gc.auto = 0`, so objects a run borrows are never pruned under it.
- **D3** [gap] TECHNICAL-SPEC §5, §7.3: `RunSpec` names the handler's tokens as `Push` and `Read` of type `ports.TokenSource` (`Token(ctx)`), not fixed tokens, so the credential helper can hand out a renewed token near the one-hour expiry (`secrets.Lease` implements it; `ports.StaticToken` wraps a fixed one). It also gains `RepoURL` (the helper serves only that host), `Runner` (`local`, the default, or `local-unsandboxed`) and `LogPath`. Why: §7.3 has the helper renew tokens; the sketch's argument types are owned by this task (ports work plan D14).
- **D4** [gap] INTEGRATION-SPEC §3.3: the cached clone is a bare repository per repository URL whose `refs/heads/*` mirror the remote's branches (`git fetch --prune --no-tags origin +refs/heads/*:refs/heads/*`), fetched before every `Prepare` under an exclusive `flock`, so runs on one host never fetch the same clone at once. A run on an existing branch gets a local branch at the remote head, tracking it; a new branch starts at the base tip with its upstream set to `refs/heads/<name>` on `origin`, so a plain `git push` creates it; review gets the commit detached. `origin` in the run's tree is the repository URL, not the cache. A commit or base branch the remote doesn't have is `ErrNotFound`; a failed fetch is `ErrTransient`. Branch names must pass `git check-ref-format --branch` and not start with `-`; a detach must be a full SHA.
- **D5** [gap] TECHNICAL-SPEC §13: the workspace root defaults to `<user cache dir>/agent-loop/workspaces` (`~/Library/Caches/agent-loop/workspaces` on macOS, `$XDG_CACHE_HOME` or `~/.cache` on Linux), with `repos/` and `runs/` (mode `0700`) inside. It is stored with symlinks resolved, so the paths in the sandbox settings are real ones. Why: it must be readable by the sandbox, so it can't sit in the state directory the sandbox denies (D9).
- **D6** [gap] TECHNICAL-SPEC §7.3: the worker's own git commands (the fetch and the run's clone) read no system or global git config (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`), never prompt, and drop every inherited `GIT_*` variable. The fetch of an `https` URL authenticates with a token from an optional callback, given to a `git credential-cache` daemon of the fetch's own on stdin; the fetch reaches it through `credential.helper` (after an empty entry) over a Unix socket in a private `0700` temp directory, and the daemon is stopped and the directory removed when the fetch ends. So the token is never in a process's environment or arguments, where other processes of the same user could read it (review R4). Which identity's token it uses is the caller's choice (T15). Why: the owner's global config may name credential helpers or URL rewrites the loop must not use.
- **D7** [gap] INTEGRATION-SPEC §3.3: `Release` deletes only a direct child of `runs/`, refuses any other path, and treats a tree that is already gone as released. Branches stay, on the remote and in the cache.
- **D8** [gap] TECHNICAL-SPEC §7.2: the settings file sets `sandbox.enabled`, `sandbox.failIfUnavailable` (Claude Code refuses to start rather than run unsandboxed), `autoAllowBashIfSandboxed`, `allowUnsandboxedCommands = false` and no `excludedCommands`; `sandbox.filesystem.allowWrite` is exactly the run's tree, `AGENT_LOOP_OUT`, the result path and the run's temp directory; `sandbox.filesystem.denyRead` is D9; `sandbox.network.allowedDomains` is the stage's egress list; `allowUnixSockets` is only the helper's socket, with `allowAllUnixSockets` and `allowLocalBinding` false. Because the sandbox wraps only Claude's shell commands, `permissions` repeat the limits for Claude's own tools: `Read(...)` deny rules for every denied path, `WebFetch(domain:...)` allow rules for the allowlist only, `additionalDirectories` for the out and temp directories, and `disableBypassPermissionsMode = "disable"` (skip-permissions is for the Docker runner only). Absolute paths in permission rules (`Read(//...)`) are written with a leading `//`, as Claude Code requires there; `sandbox.filesystem.*`, `allowUnixSockets` and `additionalDirectories` take plain absolute paths (review R3). Why: §7.2 lists what the settings must do, not Claude Code's keys.
- **D9** [gap] TECHNICAL-SPEC §7.2: the denied reads are `~/.config/agent-loop`, `~/.local/state/agent-loop` (agent-loop's state directory, which holds the default projection database, and where the server's Temporal data must live: T17 should put it there), the deployment file's directory, the API socket's directory, the projection database and its `-wal`, `-shm` and `-journal` files, the env/file secrets file, `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.netrc`, `~/.docker`, `~/.kube`, `~/.git-credentials`, `~/.config/git/credentials` and `~/Library/Keychains`. A path that is a symlink is denied under both names. Why: §7.2 names "the server's Temporal data" and "the git credential stores" without paths.
- **D10** [gap] TECHNICAL-SPEC §7.2 "Loopback and the local network are denied": `sandbox.network.deniedDomains` always holds `localhost`, `*.localhost`, `127.0.0.1`, `::1`, `0.0.0.0`, `*.local` and `host.docker.internal`, which win over any allow, and those names are dropped from the allowlist even when the profile's `egress.allow` names them. Addresses outside the allowlist are denied by the sandbox anyway.
- **D11** [gap] TECHNICAL-SPEC §7.2 "a handler that the Claude sandbox doesn't wrap": a handler is wrapped when its command's program base name is `agent-loop-claude` (the starter handlers, which run Claude Code with `--settings "$AGENT_LOOP_CLAUDE_SETTINGS"` and refuse to run without it). `runners.Wrapped` is exported for `project validate` (T18). Every handler stage is an agent stage in v0.1, so the rule applies to every run of the `local` runner. Why: the spec gives the rule but no way to tell which handlers it covers; another Claude-based handler can be added to the list when one exists.
- **D12** [gap] TECHNICAL-SPEC §7.1, INTEGRATION-SPEC §3.1, secrets D12: the handler's environment is built from scratch, not inherited. It holds `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES` and `TZ` from the worker, any names in the runner's `PassEnv` (for example an API key the agent needs), the spec's `Env`, and the runner's own `AGENT_LOOP_INPUT`, `AGENT_LOOP_RESULT`, `AGENT_LOOP_OUT`, `AGENT_LOOP_CONTRACT` (`1.0`), `AGENT_LOOP_CLAUDE_SETTINGS` (sandboxed runs), `GH_TOKEN` (the read token, when there is one), `TMPDIR` (the run's temp directory) and `GIT_TERMINAL_PROMPT=0`. `Env` or `PassEnv` naming an `AGENT_LOOP_SECRET_*` variable or one the runner sets is an error, and the handler doesn't start. So no `AGENT_LOOP_SECRET_*` variable ever reaches a handler.
- **D13** [gap] TECHNICAL-SPEC §7.3, INTEGRATION-SPEC §3.1, §3.4: the run's tree gets `credential.helper` set, in its local git config, to an empty entry (which clears every helper from the owner's global and system config) and then `!'<agent-loop>' credential-helper '<socket>'`. The hidden subcommand `agent-loop credential-helper <socket> get|store|erase` forwards git's request to the socket. The worker answers `get` with `username=x-access-token` and the push token only when the request is `protocol=https` for the host of the repository's URL; for any other request, for a review run (no push token) or for a repository that isn't `https`, it answers nothing. `store` and `erase` do nothing. The socket is `git.sock` in the run directory, mode `0600`, served until the run ends. Each token served is added to the redactor. Why: the spec names the helper and the socket, not the program or the protocol.
- **D14** [gap] TECHNICAL-SPEC §6.5, FR-18 AC4, NFR-7: at the time limit (or when the caller's context ends) the runner sends SIGTERM to the handler's process group, then SIGKILL after a grace period of 10 s (the supervisor of D20 does both for processes outside the group). When the handler exits on its own, whatever is left in its group is killed with SIGKILL. A run stopped at its time limit has `TimedOut` and exit code -1, even when the handler traps SIGTERM and exits 0 (review R2); one stopped by its context returns the context's error with the outcome. stdin is `/dev/null`, which reads as closed, rather than a closed descriptor, so a later file the handler opens can't take descriptor 0. The run log gets stdout and stderr through one pipe, so waiting for the handler doesn't wait for a process that left the group; such a process's output stops being copied a grace period after the handler ends.
- **D15** [gap] FR-18 AC3, INTEGRATION-SPEC §3.1: `ReadResult` reads `result.json` only if it is a regular file (not a symlink, FIFO or directory) of at most 1 MiB, and validates it with `contract.ValidateResult`. Anything else is a `failed` result with a one-line reason, whatever the exit code. Before starting, the runner deletes any file already at the result path, so a result from an earlier run is never read as this one's.
- **D16** [gap] TECHNICAL-SPEC §7.2 "validate then warns, in those words, on every run": a `local-unsandboxed` run logs the warning "This handler runs with the owner's full user access: it can read the owner's files, reach any network address, and open the local API socket." to the worker's log and as the first line of the run log. The local runner refuses any other `runner` value (for example `docker`).
- **D17** [gap] TECHNICAL-SPEC §7.2, §7.3: each run gets a directory `al-XXXX` under the system temp directory (kept short for the Unix socket path limit) holding `git.sock`, `claude-settings.json` (mode `0400`) and `tmp/`. The sandbox may write only `tmp/`, so a handler can't rewrite its own settings; the directory is deleted when the run ends. The run log is opened in append mode with mode `0600`, and the out directory is created if missing.
- **D20** [open] PRODUCT-SPEC NFR-7 AC1, TECHNICAL-SPEC §6.5, INTEGRATION-SPEC §3.1 (review R1): the process group alone misses a child that calls `setsid` or `setpgid`. So the runner starts each handler under the hidden subcommand `agent-loop supervise`, the handler's parent in its group. The supervisor scans the process tree by parent pid every 25 ms (`/proc` on Linux, `sysctl kern.proc.all` on macOS, through the new dependency `golang.org/x/sys`) and remembers every process it has seen below it (by pid and start time); on Linux it is also the child subreaper (`PR_SET_CHILD_SUBREAPER`), so an orphan below it is re-parented to it, and it reaps it. On SIGTERM it signals the processes outside the group too, and SIGKILL after the grace period; when the handler ends it kills everything it has found, scanning again until nothing is left, then exits as the handler did. The runner kills the group itself only if the supervisor hasn't ended 2 s after the grace period. Not covered: on macOS, which has no subreaper, a process the supervisor never saw (one whose parent started it and ended within one 25 ms scan) is re-parented to launchd and escapes; on both, a process started outside the tree (by launchd, systemd or `at`) escapes. The Claude sandbox and the token revocation at the end of the run (§7.3) limit what such a process can do. Closing it fully needs a cgroup on Linux or a container (the Docker runner); the owner should say whether that gap is acceptable for v0.1.
- **D18** [open] INTEGRATION-SPEC §3.1: `agent-loop-token read`, which gives a handler a fresh `GH_TOKEN` over the helper's socket, is not built here. The socket answers only git's operations. The runner reads `GH_TOKEN` once at the start, so the worker (T15) must issue the read token fresh for each run to meet "valid for at least 55 minutes".
- **D19** [open] INTEGRATION-SPEC §3.3, §5.3: the specs don't say which author and committer identity a handler's local commits carry. The runner sets none, so the owner's git config applies.

## Verification

Standard checks. Process-group tests check with `kill(pid, 0)` that every child is gone. No test needs `claude`, GitHub or the network.

## Risks and open questions

- A child that leaves the process group (`setsid`) is stopped by the supervisor (D20), except on macOS when it was orphaned before a scan saw it.
- The real Claude sandbox is not exercised here; the settings follow the published schema, and a live check belongs to the handlers' live test.

## Outcome

`internal/workspace` (`Git`) and the `local` runner in `internal/runners` (`Local`, `Settings`, `DeniedReads`, `Wrapped`, `ReadResult`, the credential helper) are built as planned, with the hidden `agent-loop credential-helper` subcommand for git. Tests use the test binary as the fake handler and helper client, local bare repositories as remotes, and no network or `claude`. Coverage: runners 89%, workspace 81%.

Deviations:
- The per-run tree is a shared clone of the cached clone, not a `git worktree` (D2), so a handler's commits stay inside its own directory.
- `RunSpec` changed in `internal/ports` (D3): token sources instead of fixed tokens, and `RepoURL`, `Runner`, `LogPath`.
- `cmd/agent-loop` gained the hidden subcommand, which the credential helper needs to exist (D13).

Follow-ups for later tasks, no issues filed: T15 issues a fresh read token per run and picks the fetch token (D6, D18); T17 puts Temporal's data in `~/.local/state/agent-loop` (D9); T18 uses `runners.Wrapped` for the sandbox rule (D11).
