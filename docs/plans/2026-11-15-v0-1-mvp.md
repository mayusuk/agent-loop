# Plan: v0.1 MVP

**Status:** Draft
**Base:** `origin/main @ 27884d5`
**Tracking issue:** —

## Goal

Build agent-loop v0.1 as the product spec defines it (`specs/PRODUCT-SPEC.md` §12, v0.1 row). That means one project on GitHub, run from the owner's Mac. The loop picks `ready` issues, implements them, reviews them, addresses the review and merges, all unattended. It escalates to the owner when it can't go on, and stays bounded by its limits. v0.1 is done when the end-to-end scenario in §11.1 passes against the fake adapters, and its real-repository steps pass on a GitHub test repository.

## Context

The repository holds only specs, docs and the issue workflow config. There is no code yet. Sources read:

- `specs/PRODUCT-SPEC.md`: approved. It is the source of truth, including D1–D44.
- `specs/INTEGRATION-SPEC.md`: the handler contract (§3–§5), tracker records (§6), ports (§8), the GitHub adapter (§9), conformance (§11), adoption (§12) and profile keys (§13). Decisions I1–I16 are confirmed by the owner.
- `specs/TECHNICAL-SPEC.md`: the technology (T1–T23), package layout (§3.1), core model (§4), Temporal design (§6), runners and credentials (§7), ordered rules (§8), idempotency (§9), projection (§10), API and CLI (§11), configuration (§13), testing (§14) and release mapping (§15).
- `docs/GETTING-STARTED.md`: the onboarding flow that v0.1 must support.

Repository rules (`.wf.toml`):

- Go 1.25, one module.
- The checks are gofmt, vet, build and `go test -race`, and CI runs them on Linux and macOS (NFR-3 AC1).
- `internal/core` imports only the standard library and `contract/`.
- Tests are named after the requirement IDs they prove.
- Tests never call real GitHub or a real Temporal server.

## Approach

The build follows the layers of TECHNICAL-SPEC §3:

1. **Foundations:** the module skeleton, the handler contract (`contract/v1`), the ports (`internal/ports`) and the profile and config loader (`internal/profile`). These unblock everything else.
2. **Core:** `core.Decide` is a pure, table-tested function, split into three tasks: the stage loop (implement, review, address, rounds, next stage), merge decisions, and owner and supervisor rules. It has no I/O and no Temporal code.
3. **Adapters:**
   - the fake adapter, with the shared conformance suite;
   - the GitHub `WorkTracker` and `CodeHost`, each proven by the same suite;
   - GitHub trust and rulesets;
   - secrets and GitHub App tokens;
   - the workspace and the local runner with the Claude sandbox;
   - notifiers;
   - the SQLite projection.
4. **Execution:** worker stage activities. These run a handler, validate its result and post records as the right identity (I1). They also make the base merge with no agent (D41).
5. **Orchestration:** the Temporal workflows (`DeploymentWorkflow` with pause only, `ProjectWorkflow`, `ItemWorkflow`), then the local gRPC API on a Unix socket and the CLI.
6. **Adoption:** `project validate`, `run --dry-run` and `agent-loop init`.
7. **Acceptance:** scenario §11.1 against the fake adapters and the Temporal test environment, and a live run of the scenario on a GitHub test repository.

Most tasks after the foundations can run in parallel. The core, the adapters and the runner depend only on the contract, the ports and the profile.

## Decisions

- **D1** [gap] TECHNICAL-SPEC §3.1: the rule that `internal/core` imports only the standard library and `contract/` is enforced by a Go test (`internal/core/imports_test.go`), not by golangci-lint depguard, because no linter is set up in CI. Why: it keeps the checks to the `go` toolchain. depguard can be added later without changing the rule.
- **D2** [gap] Repository conventions: tests prove requirements by name (`TestFR7AC5_...`, `TestC7_...`, `TestScenario11_1_Step3_...`). Why: the specs cite IDs everywhere, and naming makes coverage greppable.
- **D3** [gap] TECHNICAL-SPEC §15, T7, D38: the starter handlers (`agent-loop-claude`) ship with v0.1 in a separate repository, `mayusuk/agent-loop-handlers`. The owner had it created on 2026-11-15, so the e2e scenario can run with real agents. They get their own plan in that repository, started once T2 (the contract) is merged. Only the live variant of T20 depends on them.
- **D4** [open] INTEGRATION-SPEC IQ4, C13–C15, N4b: GitHub behaviours not yet verified, including whether the reviewer app's approval counts toward required approvals. They are checked by the live conformance run in T9 and T10 (`AGENT_LOOP_LIVE=1`). A mismatch is filed as a `spec` issue, not guessed.
- **D5** [gap] TECHNICAL-SPEC §14: the GitHub conformance run and the live scenario are skipped unless `AGENT_LOOP_LIVE=1` and a sandbox repository are configured, so CI stays green without credentials. Why: CI has no GitHub App credentials.

## Out of scope

- Everything the product spec puts in v0.2 or later:
  - mint and materialise (FR-9, FR-17);
  - capabilities across several hosts and agent-run slots (FR-14 AC1–AC3, FR-16 AC2);
  - the Docker runner;
  - several projects (FR-15);
  - a remote server and `notify-agent`.
- The starter handlers themselves, which are planned in `mayusuk/agent-loop-handlers` (D3).
- The Jira and GitLab adapters (D3 of the product spec).
- Packaging and installation (for example Homebrew). The getting-started guide calls this "not decided yet".

## Risks and open questions

- GitHub behaviours in IQ4 may differ from the spec (D4). If one does, the adapter task blocks with a `spec` issue.
- The polling budget (TECHNICAL-SPEC Q4) is measured in the live scenario (T20). If it's too high, the work goes to a follow-up.
- Temporal and the Claude Code sandbox are external dependencies whose behaviour must match TECHNICAL-SPEC §6.5 and §7.2. Tests use the Temporal test environment, and live checks prove the sandbox.
